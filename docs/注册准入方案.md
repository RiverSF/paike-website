## 二、注册防刷机制（现行）

取消邀请码后，注册接口是刷号的主要入口。当前按下表四道防线控制，均为进程内实现（适配单实例部署）：

| 防线 | 规则 | 位置 |
|---|---|---|
| IP 短窗口限流 | 同一 IP **10 分钟内最多 3 次**注册请求，超出返回 `429 注册请求过于频繁，请 N 分钟后再试` | `handler/registerlimit.go` |
| IP 长窗口限流 | 同一 IP **24 小时内最多 10 次**注册请求（拦长期低频刷号） | 同上 |
| 客户端真实 IP 可信 | 只采信可信代理带来的 `X-Forwarded-For`；**未配置 `TRUSTED_PROXIES` 时不信任任何请求头**，客户端 IP 取 TCP 连接地址，伪造请求头无法绕过限流 | `router.New` → `gin.SetTrustedProxies` |
| 账号唯一性 | 手机号 / 用户名全局唯一，并发注册由 DB 唯一索引兜底并返回友好提示 | `handler/user.go`、`model/user.go` |

补充说明：

- 限流按「请求次数」计数而非「成功注册数」，失败请求同样计入，避免接口被当作手机号 / 用户名的探测器；
- 命中限流时**不返回剩余次数**，只给等待时间，防止被用于探测阈值；
- 注册 IP 会写入 `user.register_ip`，便于事后审计与同 IP 聚集排查；
- 上传接口（注册证件）另有独立 IP 频控：60 秒内最多 20 次（`handler/upload.go`）；
- 登录侧另有双维度限制（`handler/loginlimit.go`）：**账号维度**连续失败 5 次锁定 30 分钟；**IP 维度** 15 分钟内失败 30 次即拒绝，挡「同一来源用大量账号各试几次」的横向撞库；
- 以上计数均在进程内，**多副本部署需改为 Redis 等共享存储**，否则实际额度会随副本数放大。

## 三、历史存档：Web 会员邀请方案（Web 端不实施，规则移至小程序）

> 以下为 2026-10-04 的设计存档，仅在小组成立小程序版时参考（见 `docs/小程序功能手册.md` 的 F2）。
> 实现时**不得复用**已删除的 `invite_code` 表，应新建独立的邀请凭证 / 奖励表。

### 3.1 三层解耦模型

```
渠道归因层  ref 短 token（可复用、无状态）→ 邀请人 ID + 注册来源
准入凭证层  小程序端：微信授权身份（无需额外准入码）
信用结算层  配额 + 延时结算 + 连坐 → 控制"有效性"与奖励发放
```

### 3.2 谁能发邀请链接

| 会员状态 | 是否可生成邀请链接 | 月配额 |
|---|---|---|
| 试用会员（trial） | **否** | — |
| 付费会员（monthly/quarterly/yearly/permanent，未过期） | 是 | 3（可动态调整） |
| 已过期 / 被冻结 / 有违规记录 | 否 | — |

配额动态调整：连续有效邀请 +1；出现垃圾号 -1；连续 2 例无效 → 暂停发链接权。

### 3.3 注册链路（被邀请人视角）

1. 分享人在个人中心点「邀请有礼」→ 复制链接或小程序码（`ref=<token>`）；
2. 被邀请人打开 → 前端自动带入 ref（只读，不可改），顶部提示"由 XXX 邀请"；
3. 后端 `GET /api/invite/resolve?ref=xxx`（公开）校验有效性并回显邀请人昵称；
4. 注册时仍需：用户名、密码、手机号（唯一性校验）；
5. 注册成功 → 写入邀请人 ID 与注册来源标记；
6. 注册即成为免费会员（试用）→ **分享人 +7 天**；
7. 被邀请人首次付费（管理员录入续费）→ **分享人再 +15 天**。

### 3.4 奖励规则

| 触发事件 | 奖励 | 到账时点 | 备注 |
|---|---|---|---|
| 被邀请人注册成功（成为免费会员） | 分享人 +7 天 | **T+7 天延时**，且被邀请人账号正常（未冻结） | 防注册即弃号 |
| 被邀请人首次付费（产生 `recharge`） | 分享人 +15 天 | 付费录入成功后 | 每个被邀请人只计一次 |
| 被邀请人被判定为垃圾号/冻结 | 回收已发奖励 | 立即 | 连坐 |

实现要点：
- 加天数统一走 `member_expire = max(member_expire, now) + days`，并写一条 `recharge` 流水（`source=self`、`amount=0`、`remark=邀请奖励`），**不得累加 `total_recharge`**；
- 奖励记录独立表（建议 `invite_reward`）：`inviter_id`、`invitee_id`、`stage`、`days`、`status`、`qualified_at`、`granted_at`、`revoked_reason`；
- 单人累计奖励上限（建议每年不超过 90 天），防薅。

### 3.5 有效性保障

| 手段 | 做法 |
|---|---|
| 延时结算 | 注册 ≠ 奖励到账；T+7 天仍活跃且未被冻结才计入有效邀请 |
| 连坐 | 被邀请人被冻结/判垃圾 → 扣配额、回收奖励，连续 2 例暂停发链接权 |
| 配额 | 每月 3 个；链接 7 天未注册自动失效回收 |
| 轻量风控 | 同 IP 24h 注册上限 3、同 `/24` 网段上限、注册失败 5 次弹滑块/图形验证码 |
| 兜底 | 管理端可按 `register_src` 筛选来源账号做抽样人工复核 |
